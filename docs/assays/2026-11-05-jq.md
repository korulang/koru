# tool-assay: jq in Koru

Target: a faithful jq — a CLI that slurps JSON on stdin, applies a filter
language over a document tree, and re-emits JSON. Assayed against
`main @ 8cb657e9e` (worktree `assay-jq`, 2026-11-03). jq's own shape is
two problems: (1) a *document model* — parse arbitrary JSON into a
walkable tree, transform, serialize; (2) a *filter language* — jq's
`.foo[] | select | map` evaluator. They are separable: a "jq-shaped"
tool with compile-time-fixed pipelines needs only (1); the full jq
language needs (1) + an interpreter, which is a different cost class.

## exists (named surface + evidence)

- **stdin slurp** — `std/io:read-stdin() | ok string<allocated!>`
  (`koru_std/io.kz:173`, `readToEndAlloc`); frees via `io:free`. Line-mode
  alternative `read-lines` streams `! line`.
- **argv** — `std/io:args {} -> []string` (`koru_std/io.kz`) — flag parsing
  (`-r`, `-c`, `-n`) is hand-rolled but the source is there.
- **JSON value union** — `JsonValue = union(enum){string,int:i64,
  float:f64,bool_val,null_val,raw}` (`koru_std/json.kz:22`) — exists for
  *construction* only (see blockers).
- **JSON construction** — `std/json:object.new/set/finish`,
  `array.new/push/finish` with `<building!>` phantom
  (`koru_std/json.kz:35-163`) — emit a correct object/array literal.
- **Typed extraction** — `std/json:get.string`, `get.int` — substring
  finders, not a DOM (`koru_std/json.kz:175`, `:212`; `indexOf` on
  `"key":"` — no nesting, no key iteration, first match only).
- **Maps with iteration** — `std/string-map` (+ `! each` arm,
  `koru_std/string-map.each.kz:19`) — dynamic string-keyed storage, the
  shape an object model wants underneath.
- **Lists** — `std/list` family (`list.new/push/get/pop/len/free`,
  `list.protos`, `list.synth`) — dynamic arrays.
- **Sorting** — `std/array:sort { expr: Expression }`
  (`koru_std/array.kz:23`) — sort-by key extraction is jq's `sort_by`
  shape.
- **String ops** — `std/string:split` (`! piece` views), `contains`,
  `index-of`, `substring`, `parse-int`, `from-int`, `read` (`! text`
  borrow-out), `std/fmt:ln`/`fmt.blk` for output interpolation.
- **Regex** — `std/regex` (`koru_std/regex.kz`, 464 lines) — jq's `test`/
  `match`/`capture` primitives have a substrate.
- **Number render** — `std/num` render/parse, `std/quantity`.
- **Records/variants** — Koru has nominal records and variant tors
  (`tests/regression/300_ADVANCED_FEATURES/370_VARIANTS/`) — the
  type machinery a document model would be declared in.

## missing-blocker (probed or cited absence)

- **JSON document model — no parse-to-tree.** `koru_std/json.parse*.kz`
  exports no public tor (the `~pub tor` inventory over
  `json.kz`/`json.parse.kz`/`json.parsehelpers.kz`/`json.parsesub.kz`/
  `json.emit.kz` yields only `object.*`, `array.*`, `get.string`,
  `get.int`, `emit.free`). The decode side is two substring scans; there
  is no tor that takes `string` and yields a traversable object/array
  value. Everything jq is — descend, select, index, iterate keys —
  stands on this. **The blocker.**
- **Object key iteration / dynamic field lookup on parsed JSON.** No
  surface: `get.string(json, key)` requires the key spelled in source
  and finds the first substring match — no `keys()`, no child enum, no
  `value[string]`-style access on a parsed node. Cited: decode section
  of `koru_std/json.kz` is `get.string` + `get.int`, nothing else.
- **A recursive, heterogeneous node type for parsed values.** The
  declared `JsonValue` union exists but `raw` nests objects/arrays as
  *unparsed text* (`koru_std/json.kz:22-30`) — construction-side only;
  no parsed-node type is exported or consumed by any public decode tor.
  Cited: `object.set`/`array.push` take `JsonValue`; nothing reads one
  back out of parsed text.
- **Heterogeneous output values round-trip.** `array.push`/`object.set`
  accept `JsonValue` — building works — but there is no walk/emit over a
  *parsed* tree (follows from the DOM gap; `emit.free` only discharges
  an emitted-text obligation, `json.emit.kz:43`).
- **Runtime-dispatched eval (full jq).** jq's filter argument is a
  program; Koru flows are compiled, not interpreted at runtime. A tool
  that *evaluates* `.foo[] | map(.id)` strings needs a jq-subset
  interpreter written in Koru — buildable only after the DOM exists;
  not a toolchain wall but real package work. Marked as its own cost
  class below rather than a compiler blocker.

## missing-but-portable (absent, workaround shape obvious)

- **JSON string escaping in output** — no `json.escape` surface cited;
  emit-side hand-rolling or a small std leaf covers it.
- **Pretty/compact output modes** — `fmt.ln` prints; a canonical
  serializer comes with the DOM work, not separately.
- **f64 vs integer output fidelity** — `std/num` render exists; jq's
  "integers print without `.0`" is formatting policy, not machinery.
- **Error diagnostics with JSON path context** — hand-rolled per tool;
  `panic`/`io:print` suffice for a CLI.
- **Recursive descent over arbitrary depth** — needed by any DOM walker;
  whether Koru subflows accept self-recursion is *unmeasured* (no probe
  this session — flag for whoever builds the DOM spike; if recursion is
  refused this column item upgrades to blocker).

## Recommendation

Commission it — but the honest scope is **a JSON document model plus a
jq-shaped CLI**, not jq-the-language. The gap map is dominated by a
single missing piece: parse-to-tree with key iteration and typed
descent. That is a **stdlib surface** cost class (new `std/json` decode
tors over the existing union + string-map/list substrate), not a
compiler feature: nothing probed suggests the language can't hold a
recursive node type — the surface simply was never written. Filter
language: a fixed-pipeline CLI (flags pick the transform) is stdlib;
runtime-evaluated jq syntax is an interpreter — **package work**, and
the correct second commission only after the DOM lands and is measured.

Cost classes: DOM = stdlib surface (medium: parse + node type + walk
API + serializer); CLI shell = small stdlib; full jq evaluator = large
package work, deferred.
