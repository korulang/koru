## The one-sentence thesis

🏗️ A compile-time Koru interpreter is **a new pipeline pass that walks the program
AST the backend already holds and *executes* its pure subset to emit constants** —
reusing the front-end's real parser output and the shared expression evaluator,
never a bespoke parser. It is a *sibling* of the transform/check passes, not a new
subsystem.

## Why this is smaller than "revive the interpreter" sounds

The parked interpreter (`src/interpreter.zig`) was shelved for two reasons, and a
*compile-time* evaluator sidesteps **both**:

1. ⚠️ **It used a bespoke parser for speed.** `src/flow_parser.zig` (~42 KB) is a
   separate, hand-rolled parser, distinct from the real front-end parser
   `src/parser.zig` (~412 KB). The interpreter's `runSource`/`runSourceFast` go
   through `flow_parser`. → **MOOT at compile time:** the AST already exists, so the
   evaluator *parses nothing*. It consumes the front-end's AST and reuses
   `ExpressionParser` for expressions. The whole reason for a fast bespoke parser
   (parsing on the wire) does not apply.
2. ⚠️ **It was a premature "Koru on the wire" experiment** with a runtime budget
   model, built before the language landed. → **IRRELEVANT at compile time:** this
   pass runs once, during backend compilation, over small comptime-bounded loops.
   ⚖️ **Optimize for CORRECTNESS, not speed.** No budget, no wire, no fast path.

So the move is **NOT to revive `src/interpreter.zig`** — it is to write something
fresh and small that reuses what already works.

## The grounded foundation — why this isn't fantasy

- ✅ **The serialized AST is already baked into the backend.** `program_ast.zig`
  emits a per-user `PROGRAM_AST` constant (`compiler.kz:113–121`, imported at
  `compiler.kz:553`).
- ✅ **The backend pipeline already walks that AST.** The metacircular coordinator
  takes it directly: `~[comptime|abstract] pub event coordinate { program_ast:
  *const Program, allocator }` (`compiler.kz:664`), `~coordinate =
  context-create(program_ast, allocator)` (`compiler.kz:671`). frontend / analysis
  / optimizer / emission all operate on `*const Program`. **The metacircular
  compiler IS an AST-walker over the serialized AST** — the interpreter is one more
  walker beside it.
- ✅ **The capture transform already operates on the parsed fold AST**, not on text:
  `! as` binds the cell, `captured {…}` invocations are rewritten into `.assignment`
  nodes, `| captured` is the after-read (`koru_std/control.kz`). No re-parse needed.
- ✅ **A shared expression evaluator exists** — `ExpressionParser` (used by the print
  family, the interpreter's condition path, etc.). Reuse it for `captured`-update
  expressions instead of inventing arithmetic.
- ⚖️ **"Restrict the subset → the problem becomes decidable"** is a proven Koru move
  (regex → DFA; the kernel's `pairwise`/`self`). The interpreter restricts to the
  *pure, comptime-bounded* subset.

## First target — scoped, with executable pins that already exist

🏗️ **The pure capture-fold evaluator.** Capture's surface already expresses array
build + index + filter + accumulate (see `2101f_nbody_arrayed_capture`:
`captured { dv[i][0]: acc.dv[i][0] - … }`). A comptime evaluator over that shape:

- seed the cell (scalar **or** array),
- iterate the `for`-ranges (comptime-known bounds),
- take `if` branches,
- evaluate each `captured` update expression (via `ExpressionParser`) over the cell
  + loop vars, including array index read/write,
- emit the final cell as a literal `const`.

⚖️ **The one hard restriction: the fold must be PURE** — comptime-known bounds, no
runtime-event calls in the body (arithmetic / `gcd` / index ops are fine;
`pair-force` is not). Table generation is exactly the pure case.

**Executable pins (currently RED, the to-do list):**
- `tests/regression/.../310_090_aspire_comptime_pure_koru_fold` — comptime
  capture-fold sum 1..9 = 45. (Note: its surface is currently stale — a `.kz` with

- `tests/regression/.../310_091_aspire_comptime_loop` — comptime `#loop`.

## The unlock

🏗️ Pure-Koru comptime *computation*, generally: wheels, gap tables, lookup tables,
any derived constant — generated by **ordinary Koru `for`/`if`/`capture` run at
compile time**, not a bolted-on DSL. This is the regex-family vision ("restricted
sub-language → native artifact") realized *in Koru itself* rather than in Zig.

Concretely it **retires the `std/table` `over`/`keep` DSL** (shipped `58668ad2`):
once a capture-fold runs at comptime, `from(wheel){ x over 0..30030 | keep
gcd(x,30030)==1 }` becomes the native

```
capture { wheel: [..]usize, n: 0 }
! as acc |> for(0..30030)
    ! each x |> if(gcd(x, 30030) == 1)
        | then |> captured { wheel[acc.n]: x, n: acc.n + 1 }
```

— no new syntax competing with the language. (See the design conversation that
produced this doc: the `over`/`keep` DSL was a route-around of exactly this gap.)

## Honest scope

- This is a **real build**, not a tweak. But it is bounded (one AST-walker over a
  pure subset) and it reuses existing infrastructure (serialized AST + pipeline
  walkers + `ExpressionParser`).
- ⚠️ **Decoupled from the prime sieve.** The sieve does **not** need this — native
  runtime `for`/`if` builds the wheel once. Do not let the sieve's momentum pressure
  this into the hacky, ballooned shape; it is a deliberate *language* investment,
  taken when the language wants it.
- ⚖️ **Correctness over speed, always.** The lesson of the parked interpreter.
