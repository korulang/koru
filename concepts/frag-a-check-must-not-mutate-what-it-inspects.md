# A check that regenerates in place turns a wrong reading into committable state (belief)

Check A verified that the generated by-example corpus matches its own
regeneration. The way it did that was to run the generators over the tracked
files and ask git for a diff. Checking and mutating were one act.

That is fine exactly as long as the regeneration is correct. The generators
derive which tests to include from live `SUCCESS` markers on disk, so a
regeneration is only well defined against a settled marker set. A second suite
running `--no-cache` clears markers before rewriting them — so a regeneration
taken during someone else's run produced an empty corpus, stripped thousands of
lines, and **left that in the working tree**.

Nothing was wrong with the comparison logic. The output was even honest: it said
the artifact differs from its regeneration, which was true. The damage is that
the wrong regeneration had already been written where the next commit would find
it, and the ceremony's step 2 is `git add -A`.

## The two rules that fall out

**A check writes nothing into the thing it inspects.** Regenerate somewhere else
and compare — the generators now take an output root, reads still coming from the
repo. A check with no write path cannot promote its own bad reading to state, no
matter how wrong the reading is. This is cheaper than making the reading reliable
and it holds when the reading is not.

**When a check's inputs are moving, it refuses.** Not "clean", not "differs" —
`CANNOT CHECK`, loudly, naming what is moving. Reporting either available verdict
would be inventing one, and *clean* is the verdict that gets believed. Check A
now detects a suite lock held by anyone but its own run and declines; the suite
exports its pid so the check can tell its own lock from a stranger's.

## Why the failure mode is specific to derived artifacts

A generated file has two truths — the bytes on disk and the inputs that produce
them — and a checker exists because those can disagree. The trap is that the
checker is also the *producer*, so its natural implementation writes. Any
verifier built by running the producer inherits this, and the tell is that
running the check twice leaves the repo different than running it zero times.

Siblings, same family, different causes: [[frag-a-watcher-off-the-normal-path-is-not-a-wall]]
(a guard the normal path never reaches) and
[[frag-a-check-that-cannot-match-reports-clean]] (a guard that runs and cannot
match). This one runs, matches, and damages the tree on its way through. All
three read as careful work.

## Read-only is not the same as robust

The sibling failure needs no write path at all. `registry_check.zig` walks the
corpus and only reads — and it died with FileNotFound, because an entry was listed
and then gone by the time it was opened. A running suite creates and removes
per-test scratch directories continuously, so every walk taken during one races
it. Non-deterministically, which is worse than always: the same `confirm` invocation
succeeded, crashed, and succeeded again.

So the rule is not "don't write." It is that a tool reading a corpus another
process is mutating must hold that condition explicitly — skip what vanished, or
decline outright — and "it only reads" is not the argument that it does.

**A concurrent suite is a first-class condition, not an anomaly.** Three tools
failed at that boundary the same afternoon, and the shared cause is not any of
their logic: it is that two agents now work one checkout, so "between runs" is a
state neither can assume. Anything walking `tests/regression` or deriving an
artifact from SUCCESS markers inherits this.

## Open

Whether anything else in the pipeline regenerates over tracked files to compare
them. `wm/worldmodel.mjs` and the site's data generators were not audited; the
ceremony runs several of them in sequence and commits immediately after, which is
the same arrangement that made this dangerous. The corpus-walking side is now
partly measured — prose-check and registry_check are held; the site's generators
are not.
