# A library with no consumer that parses it is stored, not maintained (belief)

Ten of this catalog's sixteen entry points had not parsed for an unknown but
long stretch, and the catalog looked healthy the whole time: READMEs described
working lifts, `ECOSYSTEM.md` marked them ✅ Available, the website published
five of them as documentation. Nothing was lying on purpose. Nothing had asked
the compiler.

The tell is which changes did land. Every failing file had already been
migrated from `event` to `tor` — a rename you can do by eye — while the
`[]const u8` → `string` payload rule, which only the parser can tell you about,
was missed everywhere. Sweeps that a human reading source can perform get
performed; rules that require running the toolchain get skipped, in exact
proportion to how invisible the failure is.

So the health of a library is not a property of the library. It is a property of
whether something in the loop parses it and fails loudly when it cannot. A
README is not that thing; a status table is not that thing; a page generated by
regex is *actively* not that thing, because it will keep publishing a
plausible-looking surface long after the source stops compiling. The website's
generator is now that consumer — it refuses to document what does not parse and
names the file and the diagnostic — which is the only reason this was found.

Open question: whether the catalog should also carry its own parse gate rather
than borrowing the website's. A downstream consumer noticing is better than
nobody noticing, but it means the signal only arrives when someone happens to
rebuild the site.
